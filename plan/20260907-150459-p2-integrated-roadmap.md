# WEMOVE P2 精简迭代规划：官网展示与商品运营

## 1. 目的与前置条件

本计划将 P2 收敛为一个可按时完成、可演示的官网展示版本。目标不是在本轮完成完整电商和经销商系统，而是让运营人员配置基础官网内容，让用户顺畅浏览真实商品，并保持当前购物车和订单能力不回归。

P2 开始前，成员 6 需完成 P1 的浏览器、移动端、演示账号和失败预案验收；成员 1 确认 `develop` 可从空库迁移、启动并通过 CI。本文只授权设计、开发、测试和通过 PR 合入 `develop`，不授权真实支付、生产迁移、生产部署或外部服务写入。

## 2. 本轮范围

### 必做

1. **官网框架**：固定头部、桌面导航、移动端抽屉导航、Logo、产品入口、账号入口和购物车入口；登录后按角色显示正确入口。
2. **首页基础**：Hero、分类入口、精选商品、品牌/玩法 CTA 和经销商 CTA。只支持当前所需模块，不做通用页面搭建器。
3. **商品发现**：真实 API 商品列表、分类/年龄/场景等已存在字段的筛选和排序、URL 状态、分页或 Load More、加载/空/错误状态。
4. **商品详情**：主图及可用媒体、SKU 选择、价格、年龄/场景/规格、核心卖点、加购入口和移动端布局。媒体、下载、FAQ、关联商品仅在已有 API/数据支持时接入，不为展示临时造不稳定接口。
5. **最小后台配置**：管理首页 Banner/精选商品集合/导航的基础配置，以及商品展示所需图片、标签和排序字段；草稿和受限字段不得进入公开接口。
6. **交易回归保护**：保持现有“选 SKU -> 加购 -> 下单 -> 订单查看”路径可用；继续以服务端价格、可售性和下单前库存校验为准，不新增真实支付承诺。
7. **质量基线**：桌面和移动端核心页面无明显溢出；键盘可完成导航、SKU 选择、加购和主要表单；产品图片有可用 alt；关键路径具备浏览器 E2E。

### 明确不做

- 真实支付、支付 Webhook、地址簿、配送、税费、优惠码、退款和支付型库存预占。
- 完整 Dealer Portal、企业子账号、价格等级、MOQ、报价、B2B 订单和分批发货。
- 通用 CMS、文章编辑器、媒体库版本体系、下载中心、Dealer Finder 和复杂表单线索中心。
- 全站搜索、多语言/市场、SEO 管理后台、分析报表、ERP/WMS/CRM 集成、生产监控和部署。
- MFA、刷新令牌、完整审计日志等生产安全增强；本轮只修复影响公开展示或现有交易链路的明确缺陷。

以上项目保留在后续 backlog，不应以“顺手补上”为由混入 P2 PR。

## 3. 阶段与交付门禁

### P2.0：契约与页面方案

**交付：**

- 成员 2 定义商品展示所需字段、筛选参数、公开字段与后台字段边界；Swagger 和前端类型同步更新。
- 成员 1 审查任何 Prisma migration、公开字段、角色权限和图片访问方式。
- 成员 4、5 定义首页、列表、详情、后台配置页的页面状态与共享组件边界，覆盖桌面和移动端。
- 成员 6 建立验收矩阵：公开草稿隔离、筛选、SKU 加购、订单归属、直接访问后台、移动端和键盘操作。

**门禁：** 每项页面和接口明确负责人、路由、数据来源、角色、正常/空/错误状态和测试；没有 API 契约时，前端可以完成布局但不得把 mock 合入为最终实现。

### P2.1：官网展示与商品运营

#### 3.1 公开前端

- 实现全站 Header、移动端导航和角色化账号入口。
- 实现首页的固定模块模板。后台配置变化应能影响公开首页，但模块类型和字段保持有限、可测试。
- 补全产品列表的筛选、排序、URL 查询参数、分页/Load More 与三态反馈。
- 补全产品详情的媒体呈现、SKU 选择、规格/卖点布局、加购反馈和移动端购买区域。
- 复用统一的 Button、表单、卡片、Skeleton、空状态、Toast/错误提示等共享组件，不复制视觉和交互逻辑。

#### 3.2 后台与商品数据

- 扩展商品/分类的展示字段仅限本轮前台实际使用的字段；继续区分公开 DTO 与 Admin DTO。
- 提供 Banner、精选商品集合和导航的最小管理接口与后台页面。配置必须校验、支持草稿/发布边界，并只向公开页返回已发布内容。
- 商品图片可先采用受控的图片字段或经审查的存储方案；如接入对象存储，密钥只通过环境变量提供，且本轮不上传真实客户资料。
- 现有购物车/订单继续通过成员 2 导出的商品可售性和价格规则工作；成员 3 不复制商品查询逻辑。

#### 3.3 集成与验收

- 使用独立测试数据库回归公开商品、草稿隔离、SKU 加购、库存不足、下单快照和订单越权。
- 增加浏览器 E2E：商品列表 -> 筛选 -> 详情 -> 选 SKU -> 加购 -> 下单 -> 订单详情；覆盖未登录跳转和移动端主要布局。
- 对首页、列表和详情执行生产构建后的基础 Lighthouse 抽检，记录结果但不以未设定的分数阻塞本轮。

**完成门禁：** 管理员可不改前端代码调整首页基础内容和商品展示信息；游客只能看到公开已发布内容；普通用户可通过真实页面完成既有购买路径；所有 P2.1 测试与构建通过，且没有新出现的权限泄露或交易回归。

## 4. 六人分工

| 成员 | P2 负责内容 | 交付物 | 边界 |
| --- | --- | --- | --- |
| 1 | 平台、公共契约与安全审查 | migration/权限评审、环境变量规范、公开内容边界、CI 集成 | 不实现成员 2 的商品规则或成员 3 的订单规则 |
| 2 | 商品、分类与展示数据 | 展示 DTO、筛选排序、图片/标签/排序字段、首页商品集合数据 | 不直接修改订单或支付状态 |
| 3 | 现有购物车/订单回归与接口配合 | SKU 加购/下单契约回归、订单页所需接口、交易缺陷修复 | 不新增支付、配送、报价或 B2B 功能 |
| 4 | 官网与用户前端 | Header、首页、列表、详情、加购和移动端状态 | 不访问数据库，不以 mock 或浏览器金额替代 API |
| 5 | Admin 前端与设计系统 | Banner/导航/精选商品配置页、商品展示管理、共享组件与无障碍 | 不以页面隐藏替代后端权限 |
| 6 | 测试、验收与交付 | API 回归、浏览器 E2E、移动端/键盘检查、发布清单 | 不为绕过失败用例修改业务规则 |

## 5. 依赖与 PR 规则

```text
成员 1：迁移、权限、公共契约审查
          ├── 成员 2：商品展示数据与后台接口
          │       ├── 成员 4：官网展示
          │       ├── 成员 5：Admin 配置与组件
          │       └── 成员 3：现有交易路径回归
          └── 成员 6：API、浏览器和发布验收
```

1. 先完成 P2.0 中商品展示与首页配置的 API 契约，再将前端页面接入真实数据。
2. 一个 PR 只包含一个可验收能力。推荐拆分为 `feature/catalog-display-data`、`feature/home-config-api`、`feature/storefront-experience`、`feature/admin-content-config`、`test/p2-storefront-e2e`。
3. 涉及 Prisma 的 PR 必须附 migration、空库迁移验证、Swagger/类型更新和成员 1 审查。
4. 每个 PR 合并前运行相应模块的 lint、typecheck、单测和构建；跨模块 PR 由成员 6 运行独立测试库回归。
5. 不在同一 PR 同时修改商品数据模型、购物车/订单规则和页面重构。发生契约变化时，先合入后端兼容版本，再更新调用方。

## 6. 测试与验收清单

| 类型 | 必测场景 | 负责人 |
| --- | --- | --- |
| API | 公开列表/详情只返回已发布字段；草稿、Dealer 价格和后台字段不泄露；筛选/排序参数校验 | 2、6 |
| 交易回归 | SKU 选择、加购、库存不足、下单快照、订单归属和后台越权 | 2、3、6 |
| 浏览器 | 首页、列表筛选、详情、登录跳转、加购、下单、订单查看 | 4、6 |
| 响应式与无障碍 | 360/390/768/1440 宽度；键盘导航、焦点、表单标签、图片 alt、错误提示 | 4、5、6 |
| Admin | 配置发布后前台可见；草稿仍不可见；非 Admin 接口 401/403 | 1、5、6 |
| 构建与性能 | 前后端构建、生产页面基础 Lighthouse 记录、无明显图片或布局回归 | 4、5、6 |

## 7. 风险与回滚

| 风险 | 控制与回滚 |
| --- | --- |
| 公开内容泄露草稿或 Dealer 字段 | 公开/Admin DTO 分离、角色测试；发现后立即下线配置或回退对应 PR |
| 商品字段 migration 影响现有订单 | 使用可选扩展字段、空库/升级测试；迁移须有回滚说明 |
| 首页配置变更导致空白页 | 前端提供默认安全状态；后台发布校验；回退到上一份已发布配置 |
| 页面重构破坏加购或订单 | 先保留 API 契约，成员 6 在合并前运行完整 API 与浏览器回归 |
| 范围再次膨胀 | 未列入“必做”的功能只记录 backlog，不插队进入 P2 |

## 8. 后续 Backlog

下列能力对应原计划的 P2.2、P2.3、P2.4，因工期不纳入本轮：

- 真实支付、地址簿、配送、税费、优惠码、退款和支付型库存预占。
- Dealer Portal、企业成员、价格等级、MOQ、报价、B2B 订单和发货。
- 通用 CMS、文章/FAQ/下载中心、媒体版本、Dealer Finder、联系表单线索。
- 全站搜索、多语言/市场、SEO 后台、分析报表、推荐、生产监控与部署。
- MFA、刷新令牌、完整审计日志、对象存储生产化、ERP/WMS/CRM 集成。

再次启动这些项目时，必须重新进行数据、权限、外部写入和上线风险评审；不得以本计划为生产接入授权。

## 9. P2 完成定义

P2 只有在以下条件同时满足时才完成：

1. 本文“必做”范围的 API、前端和后台页面使用真实数据，不遗留最终用途的 mock。
2. 所有涉及字段的 migration、Swagger、TypeScript 类型、种子数据和文档同步更新。
3. API、浏览器、移动端、无障碍和交易回归测试有通过记录；公开/后台/订单越权路径有 401 或 403 证据。
4. 前后端生产构建通过，成员 6 更新验收清单，成员 1 审查迁移和权限变更。
5. 未经单独授权，不进行生产部署、真实支付、生产迁移或外部系统写入。
