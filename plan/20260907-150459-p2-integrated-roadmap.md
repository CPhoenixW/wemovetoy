# WEMOVE P2 集成迭代规划：可展示、可运营、可安全成交

## 1. 文档目的与生效条件

本文把《需求规格书》中的官网展示、内容运营、B2C 交易、B2B 经销商和生产能力统一为可拆分、可验收的 P2 计划。它是后续实现的路线图和分工依据，不替代每个功能 PR 中必须提交的 DTO、Swagger、migration、测试和评审说明。

计划基线为已合入 `develop` 的 P1 商品、购物车、订单、经销商和前端最小闭环。P2 开始前，成员 6 必须完成 P1 发布清单中剩余的浏览器、移动端、演示账号和失败预案验收；成员 1 确认 `develop` 可从空库迁移、启动并通过 CI。未完成 P1 验收时，不接真实支付、不接生产数据或生产密钥。

### 1.1 目标

- 让运营人员能通过后台维护首页、商品展示、内容与媒体，前台不再依赖硬编码展示内容。
- 让用户完成从浏览商品、选择 SKU、填写地址、选择配送、支付到查看订单的安全 B2C 流程。
- 让经销商按企业权限查看目录和价格、快速下单或询价，并由后台完成审核和运营管理。
- 让系统具备上线前所需的安全、可观测性、备份、回滚、性能和验收证据。

### 1.2 非目标与约束

- P2 不以“完成需求规格书所有章节”为单次发布目标。每个阶段只交付本文件列明的可运行闭环，通过门禁后再启动下阶段。
- “库存预占记录”“支付尝试记录”等是实现候选方案，不是既有需求强制规定的表名；数据模型由 P2.0 设计评审决定。
- P1 当前的库存二次校验不等同于并发防超卖。真实支付接入前必须完成 P2.1 的库存预占方案与并发测试。
- 前端不访问数据库、不保存支付敏感数据、不以隐藏按钮代替服务端授权。跨模块调用仅使用导出的 Service 或 HTTP 契约，禁止 Controller 调 Controller。
- 不在仓库提交生产密钥、支付密钥、客户数据、数据库备份或真实经销商资质文件。

## 3. 阶段路线图与门禁

### P2.0：方案冻结与准备

**目的：** 先锁定跨模块边界，避免库存、支付、CMS 和前端各自演进导致迁移或接口返工。

**必须完成：**

1. 成员 1 组织设计评审，成员 2、3、4、5、6 共同确认以下产物：
   - B2C 与 B2B 订单状态图、支付成功/失败/重复回调/取消/退款的处理规则。
   - 库存可售量、预占、释放、过期和后台调整规则；明确 P2 是否引入库存流水、预占记录或条件更新。
   - 价格优先级、税费、运费、优惠码、地址和货币的输入、快照与错误约定。
   - CMS、媒体、下载文件、首页模块、语言/市场和权限模型；媒体的公开、注册用户、Dealer、内部四级可见性。
   - 前端信息架构、设计令牌、页面状态、移动端断点和无障碍基线。
2. 对数据结构、权限和外部写入分别形成 ADR 或设计说明；所有涉及 Prisma 的变更由成员 1 审查。
3. 在 Swagger 或版本化接口文档中冻结首批 DTO；成员 4、5 基于该契约生成/维护 TypeScript 类型。
4. 成员 6 建立 P2 测试矩阵，至少列出并发库存、支付回调、越权下载、CMS 草稿隔离、浏览器结算和移动端场景。

**门禁：** 设计文档已评审；接口、数据归属、状态机、异常响应和回滚方式明确。未达到该门禁，不创建支付生产账户、不执行真实扣款、不开始会改变库存语义的 migration。

### P2.1：商品展示、内容基础与库存可信度

**展示交付：**

- 官网固定头部、移动端抽屉导航、角色化账号入口和搜索入口。
- 首页模块化展示：Hero、分类、精选商品、品牌价值、内容、经销商 CTA、订阅入口。模块数据必须由后台或受控配置提供。
- 商品列表支持分类、年龄、场景、室内/户外、价格、库存状态的筛选和排序；筛选保存在 URL，提供空状态与可访问分页/Load More。
- 商品详情支持媒体画廊、变体联动、结构化规格、玩法说明、资料下载、FAQ、相关产品和分享 canonical URL。
- 媒体与下载基础：响应式图片、alt、文件版本、公开/受限访问边界。正式文件存储方案由成员 1 审批后接入。

**交易与平台交付：**

- 成员 2 提供服务端可售 SKU、价格计算和库存可售量 Service；商品、购物车、订单不得复制其查询规则。
- 成员 2、3 实现并验证库存预占与释放规则，覆盖并发请求、库存不足、取消、超时和后台库存变更。
- 成员 1 完成会话安全和写接口基础防护的设计落地：受限接口权限复核、登录/注册/表单限流、敏感日志脱敏、环境变量与密钥治理。
- 成员 6 建立独立测试库中的并发 API 回归；测试不得指向开发共享库或生产库。

**门禁：** 管理员更改已发布商品或首页内容后，前台展示能正确更新；匿名用户不能读到草稿、Dealer 价格或受限文件；并发测试证明预占规则不会使可售数量被重复消耗。支付尚未接入前，前台不展示真实支付承诺。

### P2.2：B2C 结算与支付闭环

**展示交付：**

- 用户中心补齐资料、地址簿、订单时间线、支付结果、配送/售后入口与账户安全入口。
- 结算页展示联系人、收货/账单地址、配送方式、税费、优惠、订单汇总与明确的失败反馈；所有金额以服务端最终结果为准。
- 订单详情展示支付、配送和售后状态，但不泄露支付敏感字段。

**交易交付：**

- 成员 3 实现地址、配送、税费和优惠码的服务端计算及订单快照。
- 选择经评审的支付服务商，在测试环境建立支付会话；Webhook 必须验证签名、具备幂等处理和失败重试/告警策略。
- 将支付成功、失败、取消、超时、退款与库存预占/释放、订单状态和审计记录连接起来。
- 成员 1 审查支付密钥隔离、回调来源验证、日志脱敏和最小权限；不保存完整卡号或 CVV。

**门禁：** 支付沙箱中可完成一次购买；重复回调不生成重复订单或重复状态变化；失败/取消/超时按规则保留或释放库存；用户只能查看自己的订单；成员 6 的浏览器 E2E 覆盖成功、失败、库存不足和重复回调场景。

### P2.3：B2B 经销商与后台运营闭环

**展示交付：**

- Dealer Portal 展示企业状态、价格等级、专属目录、MOQ、交期、快速按 SKU 下单、订单记录和报价状态。
- Admin 提供产品/变体/库存、价格与促销、订单、经销商申请、企业成员和订单异常的真实页面；页面依据服务端权限显示能力。
- 完成 Dealer Finder、经销商申请补件与激活页面，以及产品支持、FAQ、下载中心和联系表单的用户界面。

**后端交付：**

- 成员 3 扩展经销商生命周期、企业地址与成员权限、报价版本、报价转订单和 B2B 付款条款。
- 成员 2 实现价格等级、价格表、企业覆盖价、MOQ/箱规/交期等商品与价格数据边界。
- 成员 1 提供内容/媒体模块的服务端基础，审查经销商文件的签名访问、后台导出和审计边界。

**门禁：** 普通用户、Dealer、Admin 的价格、订单、文件和后台入口均经过服务端验证；经销商无法读取其他企业数据；报价历史不可被覆盖；管理员能完成审核、配置价格、查看订单和处理库存异常。

### P2.4：增长、发布与生产就绪

**展示与运营交付：**

- 产品、文章、FAQ 和下载的全站搜索、联想、无结果页与搜索分析。
- 多语言/市场内容、可售商品、货币和 hreflang；缺少翻译时按明确策略回退或不发布。
- SEO 元信息、结构化数据、Sitemap、Robots、重定向和品牌化 404。
- 转化事件、运营报表、图片性能优化、移动端和 WCAG 2.2 AA 抽检。

**生产交付：**

- staging/UAT 与生产环境分离，测试环境禁止索引且不接真实生产密钥。
- 监控前后端错误、API 延迟、数据库、Webhook、支付失败、库存同步失败和邮件失败；保留 `request_id` 便于排障。
- 完成备份、恢复演练、发布/回滚步骤、依赖漏洞扫描、权限扫描和上线清单。

**门禁：** 通过性能、安全、SEO、无障碍和跨浏览器验收；备份恢复和回滚有演练记录；成员 6 签署发布验收，成员 1 才能批准由 `develop` 合入 `main` 与部署。

## 4. 六人职责与交付边界

| 成员 | P2 最终负责模块 | 主要交付 | 不应承担/不得越界 |
| --- | --- | --- | --- |
| 1 | 平台、认证、安全、内容/媒体基础、集成治理 | ADR、Schema/迁移评审、安全会话、限流、审计、对象存储接入、staging/监控/发布 | 不替代成员 2、3 编写商品、库存、订单和 Dealer 业务规则 |
| 2 | 商品、分类、属性、SKU、库存、价格、搜索索引数据 | 可售 SKU Service、库存预占实现、价格层级、商品媒体关联、筛选/排序数据契约 | 不从订单模块写入订单或支付状态 |
| 3 | 购物车、订单、支付、配送、税费、Dealer 企业与报价 | 结算服务、支付回调、订单状态、退款、企业成员、报价和 B2B 订单 | 不直接读取 Variant 表或跨企业绕过 `companyId` 边界 |
| 4 | 官网、用户中心、B2C 前端 | 首页、PLP/PDP、搜索、账号、地址、结算、订单与售后路由 | 不直接访问数据库，不将 mock 或浏览器金额作为正式数据源 |
| 5 | Admin、Dealer 前端、设计系统、可访问性 | CMS/媒体后台、商品/库存/订单后台、Dealer Portal、共享组件与表单体验 | 不把隐藏按钮、前端路由拦截当作授权实现 |
| 6 | 测试、交付、验收与缺陷跟踪 | API/并发/支付/浏览器 E2E、移动端和无障碍验收、性能与发布清单 | 不修改业务规则或测试来绕过缺陷 |

成员 4 与 5 共享组件时，由成员 5 维护组件规范；产品业务字段由成员 2 定义，交易字段由成员 3 定义，成员 1 审核公共响应、迁移与权限变更。任何没有明确归属的新模块，先由成员 1 指定负责人后才可创建。

## 5. 依赖、PR 与集成规则

```text
成员 1：安全/存储/公共契约
          ├── 成员 2：商品、价格、库存、检索数据
          │       ├── 成员 3：结算、支付、Dealer 交易
          │       └── 成员 4、5：官网、用户、Dealer/Admin 页面
          └── 成员 6：契约、并发、浏览器与发布验收
```

1. P2.0 先合入设计说明和测试矩阵；数据库、接口或权限方案没有评审结论时，不开始相关实现 PR。
2. 一个 PR 只解决一个可验收能力。例如“库存预占 Service”“支付 Webhook”“商品媒体画廊”“首页 CMS 配置”分别建 PR，不混入无关重构。
3. 涉及 Prisma 的 PR 必须包括 migration、空库迁移验证、回滚说明和成员 1 审查；前端依赖的字段变更同时更新 Swagger、TypeScript 类型和前端调用方。
4. 外部支付、邮件、对象存储、分析或 ERP/WMS 集成必须使用测试凭据，配置只来自环境变量；生产接入需要单独授权和发布评审。
5. 所有分支从最新 `develop` 创建。合并前至少执行本模块 lint、typecheck、单测和构建；跨模块变更由成员 6 执行独立测试库回归。

建议分支前缀：

```text
feature/platform-security
feature/catalog-inventory
feature/order-payment
feature/storefront-experience
feature/admin-dealer-operations
test/p2-integration
```

## 6. 测试与验收矩阵

| 类型 | 关键场景 | 负责人 | 通过条件 |
| --- | --- | --- | --- |
| 单元/Service | 价格优先级、库存预占/释放、订单状态、报价版本、权限判定 | 1、2、3 | 正常、边界、错误和权限分支均有覆盖 |
| API/契约 | 草稿隔离、受限下载、地址/税费/优惠、Webhook 签名与幂等、企业隔离 | 1、2、3、6 | Swagger、DTO、HTTP 状态与响应一致 |
| 并发与恢复 | 同 SKU 并发结算、取消、超时、支付失败、重复回调、退款 | 2、3、6 | 不超卖、不重复建单、库存与订单状态可恢复 |
| 浏览器 E2E | 首页到产品详情、筛选、注册、地址、结算、支付结果、订单；Dealer 报价/下单；Admin 审核 | 4、5、6 | 桌面与移动端核心路径完整通过 |
| 安全 | 401/403、水平/垂直越权、限流、文件权限、日志脱敏、Webhook 伪造 | 1、3、6 | 无越权数据泄露，错误可追踪 |
| 体验与性能 | 响应式、键盘、焦点、表单错误、图片、LCP/CLS/INP、只读 API 延迟 | 4、5、6 | 满足需求规格书的 WCAG 和性能目标或记录差距 |
| 发布 | 空库迁移、Docker/staging、备份恢复、监控告警、回滚 | 1、6 | 有可复现记录和负责人签署 |

性能在 P2.0 记录当前前端生产构建体积、关键页面 Lighthouse 指标及常用只读 API 的基线；P2.4 使用同一环境、同一测试路径比较。未经授权不得对生产系统压测。

## 7. 风险、数据影响与回滚

| 风险 | 控制措施 | 回滚原则 |
| --- | --- | --- |
| 并发超卖或库存状态不一致 | 先设计预占生命周期，再做并发和失败恢复测试 | 禁用支付入口，停止新订单，按库存/订单审计记录人工修复 |
| 重复或伪造支付回调 | 签名校验、幂等键、回调日志、重试与告警 | 停用回调消费，保留原始事件和订单审计，禁止手工覆盖金额 |
| 内容/媒体误公开 | 四级访问策略、草稿隔离、短期签名 URL、权限测试 | 立即撤销公开 URL/密钥，回退发布版本并审计访问 |
| Prisma migration 破坏数据 | 先备份、空库与升级路径验证、扩展-迁移-收缩策略 | 按迁移回滚说明或恢复演练的备份操作，不在生产直接删除表 |
| P2 范围膨胀 | 每阶段门禁、单能力 PR、未列项目进入 backlog | 只发布已达到门禁的前一阶段，不为赶期跳过安全和验收 |

## 8. 每阶段完成定义

一个阶段只有同时满足以下条件才算完成：

1. 范围内路由、DTO、权限、异常、数据归属与状态机已经写入文档和 Swagger。
2. 涉及数据结构时，migration 可从空库应用，测试数据与文档同步更新。
3. 相关模块的 lint、typecheck、单测、构建通过；跨模块改动的 API、浏览器或并发测试通过。
4. 匿名、USER、DEALER、ADMIN 的正常和越权路径都有可复现证据。
5. 成员 6 更新验收记录和缺陷清单；成员 1 确认没有阻塞发布的安全、迁移或集成风险。
6. 未获得明确授权前，不执行生产部署、生产迁移、真实支付扣款或外部系统写入。

## 9. 授权与后续行动

本文仅授权团队依据既有仓库流程开始设计、拆分任务和创建本地开发 PR；不授权支付服务商开户、生产密钥配置、生产迁移、生产部署或真实支付测试。P2.0 设计评审通过后，按本文件的阶段顺序启动实现。
