# WEMOVE 项目架构与迭代路线图

本文定义课程项目的目录职责、模块边界、协作规则和实施顺序。它是团队开发的架构约定；未标记为“已实现”的目录不代表已有业务功能。

## 1. 当前系统边界

项目采用前后端分离架构。Next.js 负责官网、用户中心和经销商中心的页面渲染；NestJS 负责身份、权限和业务 API；PostgreSQL 存储核心事务数据。前端不得直接连接 PostgreSQL，权限和价格判断必须在服务端完成。

```text
浏览器
  └── frontend/ Next.js
        └── HTTP /api/v1
              └── backend/ NestJS
                    ├── auth / users / common / prisma
                    ├── products / categories
                    ├── cart / orders
                    └── dealers / admin
                          └── PostgreSQL
```

## 3. 模块边界

| 模块 | 负责人 | 当前状态 | 责任 |
| --- | --- | --- | --- |
| `common`、`prisma`、`users`、`auth` | 成员 1 | 已实现 | 基础设施、认证、用户、权限和集成治理 |
| `products`、`categories` | 成员 2 | 待实现 | 商品、SKU、分类、属性、公开商品查询 |
| `cart`、`orders`、`dealers` | 成员 3 | 待实现 | B2C/B2B 购物车、订单、经销商申请和企业隔离 |
| `frontend` | 成员 4 | 待建立 | 官网、用户中心、经销商中心、后台界面 |
| `tests` | 成员 5 | 待建立 | API 契约、关键流程和回归测试 |
| `infra` 与发布检查 | 成员 6 | 待建立 | 环境、CI、部署、监控和验收支持 |

跨模块需要调用功能时，注入并使用对方 Module 导出的 Service。禁止 Controller 调用 Controller、复制他人业务逻辑或绕过 Service 直接读写他人拥有的数据表。

## 4. 已实现基础契约

- API 前缀：`/api/v1`；Swagger：`/api/docs`。
- 认证：Bearer JWT；公开路由标注 `@Public()`。
- 角色：`USER`、`DEALER`、`ADMIN`；受限路由使用 `@Roles()`。
- 成功响应：`success`、`data`、`message`、`request_id`。
- 错误响应：`success: false`、`message`、`request_id`。
- 数据库变更：先修改 `schema.prisma`，再创建并提交 Prisma migration。

新模块在开始编码前必须确认：路由、DTO、角色、拥有的数据表、调用的上游 Service、正常/异常响应和测试用例。接口细节以 Swagger 和 [开发文档](开发文档.md) 为准。

## 5. 推荐实施顺序

### 阶段 1 已完成

完成 Docker、PostgreSQL、Prisma、User、JWT、三角色权限、Swagger、健康检查、种子数据和开发文档。

### 阶段 2 商品基础

成员 2 先实现 `Category`、`Product`、`Variant` 的 migration 与 Service，再实现公开商品列表、详情和后台商品维护接口。商品查询必须先区分公开价格和未来经销商价格，不能在前端隐藏字段代替服务端控制。

### 阶段 3 前端最小闭环

成员 4 初始化 Next.js，并优先完成登录、产品列表、产品详情、购物车入口和账号入口。所有 API 调用从环境变量读取 API 基地址；不得向浏览器暴露 `DATABASE_URL` 或 JWT 签名密钥。

### 阶段 4 订单和经销商

成员 3 在商品模块稳定后实现购物车、订单和经销商申请。经销商正式上线前必须增加 `DealerCompany` 与 `DealerMember`，以企业 ID 为所有 B2B 查询的服务端数据边界。

### 阶段 5 后台与集成验收

实现 Admin 聚合接口与后台页面，补齐产品、订单、经销商和用户的权限测试。成员 5 在 `tests/` 中建立注册、商品浏览、加购、下单、经销商申请和越权访问的端到端测试。

### 阶段 6 生产能力

在课程 P1 之外，逐步评审细粒度 RBAC、审计日志、MFA、刷新令牌、限流、对象存储、邮件、支付、队列、搜索、监控和 staging/production 部署。每项涉及身份、支付、企业数据或外部写入的能力都需要单独设计评审。

## 6. 团队工作方式

1. 从 `develop` 创建 `feature/<module>` 分支。
2. 一个功能提交应包含代码、DTO、Swagger、测试和 migration（如涉及数据结构）。
3. 合并前运行 `npm run lint`、`npm test`、`npm run build`；数据变更还需运行 migration。
4. 通过 Pull Request 合入 `develop`，至少一名成员审核。
5. `main` 只接收可启动、可迁移、通过 CI 的集成版本。

## 7. 阶段验收

每个阶段结束时，至少满足：本地 Docker 环境可启动、迁移可从空库应用、关键 API 在 Swagger 可测试、未授权/越权场景有明确 401/403、相关单元或集成测试通过，且文档已同步。
