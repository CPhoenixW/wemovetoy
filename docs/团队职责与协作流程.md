# WEMOVE 团队职责与协作流程

本文为六人课程团队的推荐分工。成员可以在不改变模块边界的前提下互相支持，但每个模块只能有一名最终负责人。

| 成员 | 角色 | 主要责任 | 阶段交付 |
| --- | --- | --- | --- |
| 1 | 架构与后端基础负责人 | Nest/Prisma/Docker、用户、认证、权限、API 规范、migration 审核、集成与代码 review | 可运行基础后端、Swagger、CI、集成版本 |
| 2 | 商品域后端负责人 | 分类、属性、商品、SKU、媒体关联、公开查询和后台商品 API | 商品 schema/migration、ProductsService、产品 API 与测试 |
| 3 | 交易与经销商后端负责人 | 购物车、订单、结算准备、经销商申请、企业成员、授权价格边界 | Cart/Order/Dealer API、状态流转、企业隔离测试 |
| 4 | 官网与用户前端负责人 | Next.js 公共页面、产品列表/详情、登录、用户中心、移动端适配 | 公共路由、用户身份流程、API 对接 |
| 5 | 业务前端与设计系统负责人 | 经销商中心、Admin 前端、共享组件、表单体验、可访问性 | Dealer/Admin 路由、设计组件、权限态界面 |
| 6 | 测试、交付与项目集成负责人 | 测试计划、跨端验收、CI 维护、缺陷跟踪、环境与上线检查 | E2E 测试、验收报告、发布检查清单 |

## 成员 1：架构与后端基础

拥有 `backend/src/common`、`prisma`、`users`、`auth`、Docker 与 CI。负责审查所有 Prisma migration、Service 依赖和角色控制；不代替成员 2、3 实现业务模块。交付标准是基础服务可启动、API 规范统一、其他成员可独立开发。

## 成员 2：商品域

拥有 `products`、`categories` 及其数据库表。必须先定义 Product/Variant/Category 的 DTO、状态和公开字段，再编写 API。向其他模块导出 `ProductsService`；订单和购物车禁止复制商品查询或自行修改商品表。

## 成员 3：交易与经销商

拥有 `cart`、`orders`、`dealers` 及关联表。依赖成员 2 稳定的商品 Service 和成员 1 的认证能力。订单必须保存价格和商品快照；经销商数据必须经由 `companyId` 服务端过滤。支付接入、真实库存扣减和物流不在当前 P1 范围内。

## 成员 4：官网与用户前端

拥有 `frontend/src/app` 下的公开页面和用户中心路由。使用 `lib/api` 调用后端，不直接访问数据库。产品 API 未完成前可使用接口 mock，但不得把 mock 数据当作正式数据源提交为最终实现。

## 成员 5：经销商、后台与设计系统前端

拥有经销商中心、Admin 页面和共享组件规范。必须依据服务端返回的角色和权限显示界面，不将“隐藏按钮”当作权限控制。与成员 4 共同维护可复用组件和响应式/无障碍标准。

## 成员 6：测试、集成与交付

拥有 `tests/`、验收记录和缺陷清单。维护登录、商品浏览、购物车、订单、经销商申请与越权访问的测试矩阵。负责在合并前确认 Docker、迁移、前后端构建和关键路径通过，但不修改业务规则来绕过失败用例。

## 协作规则

1. 每项任务先确定负责人、模块、API、数据模型、依赖与验收条件。
2. 只修改本人模块；公共文件、Prisma schema、API 响应和权限策略需要成员 1 review。
3. 数据库改动必须提交 migration，其他成员合并后先执行 migration 再启动。
4. 前端以 Swagger 与 TypeScript API 类型为契约；后端变更接口时同步更新 Swagger 和相关前端负责人。
5. 提交 Pull Request 前运行本模块测试；合入 `develop` 前由成员 6 执行跨模块检查。
6. `main` 只保留可构建、可迁移、CI 通过的版本；日常开发使用 `develop` 和 `feature/<module>` 分支。

## 依赖顺序

成员 1 的认证与基础设施已就绪。成员 2 完成商品服务后，成员 4 可以联调产品页面；成员 3 基于商品服务实现交易与经销商；成员 5 等成员 3 的 API 稳定后接入 Dealer/Admin 页面；成员 6 从阶段 2 起持续补充验收和回归测试。
