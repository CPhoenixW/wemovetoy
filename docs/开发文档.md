# WEMOVE SPORTS 开发文档

本文面向课程项目的 6 人开发团队。当前集成版本提供可运行、可扩展的后端底座，并已合入商品、购物车、订单和经销商的基础模块。

当前商品 API 已可供前端联调；购物车和订单的价格、商品快照与库存校验仍需成员 2、3 基于稳定的 SKU 服务完成，不应将当前占位逻辑视为交易完成。

## 1. 技术与目录

后端采用 NestJS + TypeScript，数据层使用 PostgreSQL + Prisma；Docker Compose 只运行本地 PostgreSQL，后端在宿主机以热更新方式运行。

```text
wemovetoy/
├── backend/
│   ├── prisma/                 # Prisma schema、迁移、种子脚本
│   ├── src/
│   │   ├── auth/               # 认证与 JWT（成员 1）
│   │   ├── users/              # 用户查询与安全映射（成员 1）
│   │   ├── common/             # 守卫、装饰器、异常和响应规范（成员 1）
│   │   ├── prisma/             # PrismaService（成员 1）
│   │   ├── health/             # 健康检查（成员 1）
│   │   ├── access/             # 角色守卫验证端点（成员 1）
│   │   ├── products/           # 商品（成员 2，后续）
│   │   ├── categories/         # 分类（成员 2，后续）
│   │   ├── cart/               # 购物车（成员 3，后续）
│   │   ├── orders/             # 订单（成员 3，后续）
│   │   └── dealers/            # 经销商（成员 3，后续）
│   └── package.json
├── docs/
├── docker-compose.yml
└── .env.example
```

若成员 4-6 负责前端、测试、部署或产品设计，应通过 API 契约、Swagger 和模块 Service 与后端协作，不应绕过接口直接连接开发数据库。

## 2. 本地环境与配置

要求安装并启动 Docker Desktop，安装 Node.js 与 npm。请以仓库根目录的 `.env.example` 创建 `.env`：

```bash
cp .env.example .env
```

根目录 `.env` 是 Compose 和后端共用的唯一模板。至少检查以下变量是否符合本机环境：

| 变量 | 用途 | 开发默认值 |
| --- | --- | --- |
| `POSTGRES_DB` | 本地数据库名 | `wemove` |
| `POSTGRES_USER` | 本地数据库用户 | `wemove` |
| `POSTGRES_PASSWORD` | 本地数据库密码 | 仅限开发的示例密码 |
| `POSTGRES_PORT` | 宿主机 PostgreSQL 端口 | `5432` |
| `DATABASE_URL` | Prisma/后端连接串 | 指向上述本地 PostgreSQL |
| `PORT` | 后端 HTTP 端口 | `3000` |
| `JWT_SECRET` | JWT 签名密钥 | 必须替换示例值 |
| `JWT_EXPIRES_IN` | JWT 有效期 | `1d` |

`.env` 不进入版本控制。开发环境可以使用示例 PostgreSQL 密码；任何共享、演示或部署环境都必须改为独立的强密码与随机 JWT 密钥。

## 3. API 基础约定

所有业务 API 使用全局前缀 `/api/v1`。Swagger 位于 `/api/docs`，不使用版本化前缀；其 JSON 文档位于 `/api/docs-json`。健康检查为：

```http
GET /api/v1/health
```

认证接口由 `auth` 模块维护：

| 接口 | 认证 | 说明 |
| --- | --- | --- |
| `POST /api/v1/auth/register` | 否 | 注册普通用户，角色固定为 `USER` |
| `POST /api/v1/auth/login` | 否 | 邮箱和密码登录，返回访问令牌与安全用户信息 |
| `GET /api/v1/auth/me` | Bearer JWT | 获取当前用户信息 |
| `GET /api/v1/health` | 否 | 服务健康检查 |
| `GET /api/v1/admin/ping` | `ADMIN` JWT | 验证管理员角色守卫 |
| `GET /api/v1/dealer/ping` | `DEALER` JWT | 验证经销商角色守卫 |

需要登录的接口通过 `Authorization: Bearer <accessToken>` 传递 JWT。不要通过请求体或 URL 传递令牌。

### 成功响应

全局拦截器将正常业务结果包装为：

```json
{
  "success": true,
  "data": {},
  "message": "success",
  "request_id": "请求追踪 ID"
}
```

分页接口的 `data` 统一采用：

```json
{
  "items": [],
  "total": 100,
  "page": 1,
  "pageSize": 20
}
```

### 错误响应

全局异常过滤器返回：

```json
{
  "success": false,
  "message": "Unauthorized",
  "request_id": "请求追踪 ID"
}
```

参数验证失败时 `message` 可能是错误信息数组。认证缺失或令牌无效返回 401；已登录但角色不匹配返回 403；重复唯一字段通常返回 409。Controller 和 Service 不应自行发明另一套响应外层结构。

## 4. 认证、角色与模块依赖

P1 只有三个角色：`USER`、`DEALER`、`ADMIN`。后续受限接口使用 `JwtAuthGuard`、`RolesGuard` 和 `@Roles()`：

```ts
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('ADMIN')
@Get()
findAll() {}
```

全局 JWT 守卫默认要求认证；明确公开的接口应使用 `@Public()`。公开商品浏览、管理后台、经销商专属价格等后续接口必须在实现时明确标注权限，不允许仅依赖前端隐藏入口。

模块之间通过 Module 导出的 Service 调用。例如订单模块需要商品信息时，应注入 `ProductsService`，不能复制商品查询逻辑、直接复用另一模块的私有 Prisma 查询，或从 Controller 调用 Controller。

成员 1 负责 `auth`、`users`、`common`、`prisma` 和基础集成；成员 2 负责 `products`、`categories`；成员 3 负责 `cart`、`orders`、`dealers`。其他成员应在开始新模块前明确其归属和 API 契约。对公共 schema、权限和响应结构的变更须先在团队内同步。

## 5. Prisma 迁移规范

数据库结构只通过 `backend/prisma/schema.prisma` 和 Prisma Migration 变更。禁止在共享数据库中手动建表、改字段，禁止删除其他模块字段，也禁止只改 schema 而不提交迁移目录。

新增字段或模型的标准流程：

```bash
cd backend
# 修改 prisma/schema.prisma 后
npm run prisma:migrate -- --name add_product_stock
npm run prisma:generate
```

将以下内容一并提交：schema 变更、`prisma/migrations/<时间戳>_<名称>/migration.sql`、受影响模块代码与测试。其他成员拉取新代码后在本地执行：

```bash
cd backend
npm run prisma:generate
npm run prisma:migrate
```

开发中可以使用 `prisma migrate dev`（封装于 `npm run prisma:migrate`）。需要将已提交迁移应用到非交互环境时使用 `npm run prisma:deploy`，不要在该环境创建新迁移。迁移失败时先保留错误输出和现有数据库，团队确认原因后再修复；不要为了“重试”直接删除共享数据。

## 6. 代码、测试与 Git 协作

新增接口应包含 DTO 校验、Swagger 注解、正常路径测试，以及必要的 401/403/参数错误路径测试。提交前至少执行：

```bash
cd backend
npm run lint
npm test
npm run build
```

推荐分支结构：`main` 仅保留稳定版本；`develop` 用于集成；在 `feature/auth`、`feature/product`、`feature/order`、`feature/dealer` 等功能分支开发。不要直接向 `main` 开发。

提交信息采用 Conventional Commits 风格，例如：

```text
feat(product): add product CRUD
fix(dealer): prevent normal users reading dealer price
refactor(common): unify api response
```

功能完成后创建合并请求或由至少一名成员审阅再合入 `develop`。合并前同步 `develop`、解决冲突并验证启动、迁移、测试；`develop` 应始终能启动。不要将依赖安装目录、构建产物、本地数据库数据、`.env` 或密钥提交到仓库。

## 7. 安全边界与 P1 排除项

密码只保存 bcrypt 哈希，任何日志、响应、Swagger 示例和测试快照都不得输出密码或 `passwordHash`。JWT 密钥只存在于环境变量；开发种子密码不得用于真实用户。CORS 来源在部署前必须收紧到实际前端域名。

当前集成不包含：细粒度 RBAC 表、MFA、刷新令牌与 Cookie 会话、限流、审计日志、支付、真实库存扣减、文件上传、生产部署和生产数据迁移。实现这些能力前需要单独进行数据和安全设计评审。
