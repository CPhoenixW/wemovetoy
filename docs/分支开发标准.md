# WEMOVE 分支开发标准

本文规定团队从 2026-09-06 起的分支、合并和交付方式。目标是让 `develop` 始终保持可迁移、可启动、可测试，避免再次出现多条分支分别完成模块却无法联调的情况。

## 1. 分支角色

| 分支 | 用途 | 谁可以写入 | 合入条件 |
| --- | --- | --- | --- |
| `main` | 已验收的稳定版本 | 成员 1 负责发布 | 仅从 `develop` 合入；CI、Docker API 冒烟测试和阶段验收全部通过 |
| `develop` | 唯一日常集成线 | 成员 1 合并 PR | 所有功能分支以它为目标；禁止强制推送和直接提交业务代码 |
| `feature/<模块>-<任务>` | 单一功能开发 | 对应模块负责人 | PR 审查和所需检查通过后合入 `develop` |
| `fix/<模块>-<问题>` | 缺陷修复 | 对应模块负责人 | 回归测试证明缺陷被修复后合入 `develop` |
| `test/<范围>-<任务>` | 测试、CI、验收记录 | 成员 6 | 不修改业务规则；通过 PR 合入 `develop` |
| `docs/<主题>` | 文档或协作规范 | 文档责任人 | 不改变业务行为；通过 PR 合入 `develop` |

不要再创建 `develop2`、`develop-final`、`new-develop` 一类并行集成分支。临时集成只能在个人分支完成，最终只能合入 `develop`。

## 2. 开发流程

1. 开始任务前，从最新 `develop` 创建自己的分支，并在任务说明中写明模块、负责人、依赖和验收条件。
2. 一个分支只解决一个可验收问题。例如 SKU 公开接口和购物车真实定价必须分成两个 PR，不能把无关页面、重构或环境改动混入。
3. 开发期间，公开 API、Prisma schema、migration、角色权限和统一响应结构的修改必须同步成员 1；前端接口变更必须同步成员 4 或 5。
4. 提交 PR 前，同步 `develop`。个人独占分支可以 rebase；已有多人共同使用的分支只能合并 `develop`，不得改写历史。
5. PR 目标分支固定为 `develop`。成员 1 负责合并，成员 6 确认跨模块检查；`main` 不接受功能分支 PR。

推荐命名：

```text
feature/products-variant-admin
fix/cart-invalid-variant
feature/storefront-product-detail
feature/admin-dealer-api
test/order-checkout-e2e
docs/branch-development-standard
```

## 3. PR 最小要求

每个 PR 描述必须说明：

- 改动的模块和负责人；
- API 路由、请求/响应或权限是否改变；
- 是否包含 Prisma schema 与 migration；
- 本地执行过的命令和结果；
- 对前端、测试或其他模块的依赖。

后端代码至少通过：

```bash
cd backend
npm run prisma:generate
npx prisma validate
npm run lint
npm test -- --runInBand
npm run build
```

前端代码至少通过：

```bash
cd frontend
npm run typecheck
npm run lint
npm run build
```

需要启动服务、改动 migration、认证、权限、商品、购物车、订单或经销商模块时，PR 还必须通过 GitHub Actions 的 Docker PostgreSQL API 冒烟测试。该测试只能使用独立测试库，不得指向开发或生产数据库。

## 4. 数据与接口规则

- 数据库结构只通过 Prisma schema 和新 migration 变更；禁止修改已提交的 migration。
- 购物车和订单只能调用商品模块导出的 Service 获取 SKU 价格、名称和可售状态，不能自己查询或复制商品定价逻辑。
- 公开接口只能返回公开字段；经销商价、后台字段和草稿数据必须由服务端按角色过滤。
- 新增受保护接口必须同时验证：未登录 401、角色不匹配 403、合法角色成功。
- 新增或修改接口时更新 Swagger、前端类型和相关 API 测试；不能靠前端隐藏按钮代替权限控制。

## 5. 合并与回退

- 合并前不允许用“CI 绿了”替代业务验收。新增业务功能必须有对应正常、异常和权限测试。
- 失败的 CI 必须修复源代码或测试，不降低规则绕过。
- 禁止向 `develop` 或 `main` 使用 `git push --force`。紧急回退采用新的 revert commit，并记录原因。
- 只有成员 1 可以将阶段验收后的 `develop` 合入 `main`；合入前由成员 6 确认完整冒烟测试和发布清单。

## 6. 当前迭代顺序

1. 成员 2 先完成 SKU 数据、公开商品边界和商品接口修复。
2. 成员 3 基于成员 2 稳定的 Service 接通购物车和订单真实价格、库存校验与快照。
3. 成员 4、5 在接口稳定后移除 mock，接入真实 API。
4. 成员 6 扩展为“选 SKU -> 加购 -> 下单”端到端测试。
5. 成员 1 处理集成、migration 审查、CI、共享配置和最终合并。
