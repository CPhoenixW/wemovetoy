参考依据
本需求以现有品牌站的改版目标为主，并参考公开可检索到的 WEMOVE SPORTS 产品信息。公开资料显示品牌以运动游戏玩具为主，包括儿童保龄球套装、平衡板等产品，强调儿童运动、协调能力与亲子互动。新站应保持这一产品方向，但视觉和信息架构采用更成熟的品牌官网标准。
现有域名在本次需求整理时无法从审阅环境稳定打开，因此不对现有页面逐项复制。重构时应从原站、服务器或运营方处导出现有产品图、Logo、文案、下载资料和联系信息，再按本文件的数据结构迁移。

支付、物流、税务、ERP、WMS、CRM、邮件服务可先通过标准接口接入，具体供应商可在开发阶段确定。

1. 项目目标与产品定位
1.1 重构目标
将网站从静态页面改为后台可维护的动态站点，运营人员无需修改代码即可更新产品、Banner、内容、经销商资料、下载文件和 SEO 信息。
建立统一产品中心。产品数据只维护一份，可用于官网展示、用户购买、经销商价格、内容推荐和搜索。
建立经销商体系。经销商可在线申请、审核、登录、查看专属价格和资料、提交订单或询价，并查看业务记录。
建立用户体系。消费者可注册、收藏、维护地址、查看订单和售后记录；不登录也可以浏览完整产品信息。
建立运营后台。管理员可管理权限、商品、价格、订单、内容、经销商、用户、表单、下载资源、SEO、数据和系统配置。
提升品牌呈现。首页和产品页应以真实产品和使用场景为主，不使用大面积无意义装饰，不采用儿童网站常见的杂乱卡通风。
提升搜索与自然流量。产品详情、分类、文章和经销商页面具有独立 URL、结构化数据和可编辑元信息。
建立可度量的转化链路。关键按钮、表单、注册、经销商申请、询价、加购、下单等行为全部进入分析体系。

1.3 产品原则
=== TABLE ===
原则 | 具体要求
信息优先 | 任何视觉设计都不能牺牲产品名称、年龄、规格、用途、价格、按钮和关键信息的可读性。
一个数据源 | 产品、经销商、订单、内容等核心实体不能在多个后台重复录入。
角色隔离 | 普通用户不得看到经销商价格，经销商不得访问后台管理权限，后台操作必须按权限记录。
配置优先 | 首页模块、导航、Banner、产品排序、推荐位、FAQ、页面 SEO 等应配置化。
移动优先 | 手机端不是桌面版缩小。导航、筛选、表单、产品图、表格和操作按钮均需重新排布。
可扩展 | 新增语言、市场、价格层级、经销商类型和产品分类时不应要求重构网站。
安全默认 | 敏感操作需要鉴权、日志、限流；后台和经销商中心默认采用更严格的登录安全策略。

2.2 权限机制
采用 RBAC 角色权限模型，并允许管理员针对单个内部账号增加或移除权限。
权限粒度至少达到模块、动作两级，例如产品查看、产品新增、产品编辑、产品发布、产品删除、产品导出。
经销商权限以企业为数据边界。一个经销商企业下的成员只能查看本企业的价格、订单、报价、地址和文件。
所有后台修改应记录操作人、时间、对象、动作、变更前值与变更后值。
删除关键业务数据采用软删除或归档，不允许普通管理员直接物理删除订单、付款、报价、经销商审核记录。
后台高风险操作包括角色权限修改、退款、价格批量修改、数据导出、API 密钥修改，应要求二次验证或重新输入密码。

4.2 首页
首页结构必须由后台模块化配置，运营人员可以调整模块顺序、上下线、标题、图片、链接和产品集合，不依赖开发发布。
推荐页面结构
1.  首屏 Hero。使用真实产品或家庭使用场景图，包含一句清楚的品牌主张、1-2 个主要按钮。
2.  主推产品分类。使用 3-5 个简洁分类卡，例如 Bowling、Balance & Coordination、Outdoor Games。
3.  Featured Products。横向或网格展示 4-8 个产品，显示主图、名称、年龄、核心用途和按钮。
4.  Play Together 内容区。以真实场景内容连接到玩法文章或活动指南。
5.  品牌价值区。用 3-4 个事实型信息展示运动、亲子、易用、安全等信息。
6.  经销商入口。分别提供 Find a Dealer 与 Become a Dealer。
7.  质量与安全入口。链接到专页并可展示可验证的测试、材料、说明书或证书。
8.  内容/文章模块。用于 SEO 和持续更新。
9.  邮件订阅。明确说明订阅内容并要求隐私同意。

4.4 产品详情页
产品详情页是网站最重要的转化页面。内容应完整，不应只放主图和几句宣传文案。
=== TABLE ===
ID | 区域 | 要求
PDP-001 | 媒体画廊 | 支持主图、细节图、场景图、尺寸图、包装图、短视频。缩略图可切换，移动端支持滑动。
PDP-002 | 基础信息 | 产品名、SKU、简短卖点、适用年龄、场景、状态、评分或评论开关。
PDP-003 | 价格 | 游客/用户显示零售价；经销商显示授权价格；未授权经销商不可通过接口获取经销商价。
PDP-004 | 变体 | 如同一产品有颜色、套装、包装等变体，切换变体后同步更新 SKU、媒体、库存、价格。

PDP-008 | 玩法与说明 | 展示 Setup、How to Play、Care、Safety Notes。支持图文或视频。
PDP-009 | 下载资料 | 说明书、产品目录、合规文件、图片资料等按权限显示。

4.5 产品比较
允许最多选择 4 个产品。

5.2 B2C 购物能力
购物车支持游客态，本地保存并在登录后合并。
结算支持联系人、收货地址、账单地址、配送方式、优惠码、支付方式、订单确认。
库存不足时在加入购物车和提交订单两个节点校验。
价格、折扣、运费和税费在最终提交前展示明确，不隐藏强制费用。
支付成功后创建已支付订单；支付失败不应创建重复正式订单。
支付回调必须签名验证并具备幂等处理。
如品牌暂不做 B2C 销售，后台应能按市场关闭零售价格、购物车和结算，并自动改为 Where to Buy 或 Contact。

6.4 经销商价格体系
支持 Price List 和 Dealer Tier。示例：Distributor、Wholesale、Retail Partner。名称由后台配置。
价格优先级建议为：经销商专属价格 > 经销商价格表 > 经销商等级价格 > 默认 B2B 价格。
价格可按 SKU、币种、国家/区域、生效时间和失效时间维护。
支持阶梯价，如 1-5 箱、6-20 箱、21 箱以上。
任何价格更新应保留历史；订单成交价在订单中固化，不随当前价格变化。

8. 业务流程与状态机
8.1 经销商申请流程
1.  申请人填写表单并验证邮箱。
2.  提交后生成申请编号，状态为 Submitted。
3.  经销商运营进入审核，可改为 Under Review。
4.  资料不足时发送补件请求，申请人通过安全链接补充资料。
5.  审核通过后创建 Dealer Company 和主账号，设置价格等级、币种、付款条款、授权区域。
6.  主账号收到激活邮件并设置密码，首次登录接受经销商条款。
7.  后续状态可变更为 Suspended 或 Closed，所有变化保留历史。
8.2 产品发布流程
1.  商品运营创建 Draft。
2.  录入基础信息、媒体、规格、变体、价格、下载、SEO。
3.  后台进行必填校验，包括 SKU 唯一、主图、分类、市场和状态。
4.  可直接 Publish 或 Scheduled。
5.  发布后生成或更新前台页面、搜索索引和 Sitemap。
6.  归档产品保留 URL；默认返回产品已停售状态并推荐替代品，而不是直接 404。
8.3 B2C 订单流程
=== TABLE ===
阶段 | 典型状态 | 说明

提交 | Pending Payment | 生成待支付订单或支付会话。

异常 | Payment Failed / Cancelled | 保留失败/取消原因。
售后 | Return Requested / Refunded | 支持退货与退款流程。
=== END TABLE ===

=== TABLE ===
阶段 | 典型状态 | 说明

8.5 报价流程
Request → Under Review → Quoted → Accepted / Rejected / Expired → Converted to Order。任何价格变化以报价版本为单位保存。
9. 商品、价格、库存与订单规则
9.1 商品主数据规则
Product 是面向用户的商品页面实体，Variant 是可交易 SKU。无变体产品也建议内部生成一个默认 SKU。
SKU 全局唯一，产品 slug 在同一语言/市场内唯一。
条码可选，但存在时应唯一。
分类、年龄、场景、技能等用于筛选的字段必须结构化。
停售产品不删除历史订单关联。
9.2 价格计算优先级
=== TABLE ===
价格计算规则 / 系统先确定市场和币种，再确定账号角色。普通用户读取零售价和有效促销；经销商按企业专属价、企业价格表、经销商等级价、默认 B2B 价依次匹配。阶梯价根据有效采购数量计算。订单提交时固化成交价、币种、税费、折扣和价格来源。
=== END TABLE ===
9.3 库存与预占
订单确认前再次校验库存。
支付型订单可在创建支付会话时短暂预占，超时释放。
B2B 审核型订单的预占时点可配置为提交时或确认时。
库存同步失败时前台不应显示旧的精确数量，可降级为联系确认或暂停售卖。
9.4 税费和运费
税费采用独立 Tax Service 接口层，便于接入第三方税务服务。
运费支持固定费、按重量/金额区间、免运费阈值和第三方实时运价。
经销商可配置自有物流、到付或线下运费确认。
所有计算结果在订单中保存快照，避免规则变化后历史订单金额改变。

同一产品需尽量具备主图、细节图、包装图、尺寸图、场景图。

12. 多语言、SEO 与分享
12.1 多语言与市场
语言与市场分离。一个市场可用多语言，一个语言也可用于多个市场。
所有可公开内容支持翻译状态：Not Started、In Progress、Ready、Published。
产品 SKU、库存等主数据共享；产品名称、描述、SEO、文章等内容按语言维护。
URL 建议使用 /en-us/、/zh-cn/ 等可识别语言市场路径，或按业务实际选择。
使用 hreflang 关联等价语言页面。
缺少翻译时由后台策略决定回退默认语言或不发布，不应出现半页英文半页中文。

13. UI/UX 与视觉规范
13.1 视觉方向
新站的视觉应体现运动、家庭互动和产品本身。设计重点是结构、留白、摄影和字体，而不是大量装饰。
=== TABLE ===

强调色 | 用于主要 CTA、状态和活动，不在同一页面使用过多高饱和颜色。
字体 | 英文采用清晰无衬线字体，中文采用系统兼容无衬线字体；正文避免过细字重。

动效 | 用于反馈和状态变化；不使用长时间自动播放、频繁视差或干扰阅读的动画。

视频提供字幕或文本摘要；不自动带声音播放。

15. 接口与第三方集成
15.1 集成原则
对外部系统使用独立 Service Adapter，业务代码不直接依赖单一供应商 SDK。
所有写入型 Webhook 进行签名验证、重放防护和幂等处理。
外部服务失败时有重试、告警和人工补偿机制。
API 密钥和机密信息不保存在代码仓库和前端。
15.2 推荐集成点
=== TABLE ===
类别 | 可选方案 | 用途
支付 | Stripe、Adyen、PayPal 或本地支付 | B2C 支付，经销商信用卡支付可选。
邮件 | Amazon SES、SendGrid、Postmark | 事务邮件与系统通知。
对象存储/CDN | S3 兼容存储 + CDN | 图片、文件、经销商私有资料。
搜索 | Algolia、OpenSearch、Elasticsearch | 商品与内容搜索。
ERP/WMS | 现有内部系统 | 产品、库存、订单、发货、发票同步。
税务 | TaxJar、Avalara 或本地服务 | 按市场计算税。
物流 | Shippo、EasyPost、承运商 API | 运价、面单、追踪。
分析 | GA4、GTM、服务端事件仓库 | 行为分析与转化。
客服/CRM | HubSpot、Zendesk 或现有 CRM | 线索和客服同步，可选。
=== END TABLE ===

15.3 API 设计要求
API 版本化，例如 /api/v1。
使用一致错误结构：code、message、field_errors、request_id。
列表接口支持分页、排序、筛选，并限制单页最大数量。
后台批量操作采用异步任务时需要任务状态与失败明细。
经销商价格和私有文件接口必须在服务端校验企业权限。
所有重要接口返回 request_id，便于排查。
16. 安全、隐私与合规
16.1 账户与访问安全
=== TABLE ===
ID | 项目 | 要求
SEC-001 | 密码 | 使用现代自适应哈希算法；后台不可恢复明文密码。
SEC-002 | MFA | 后台强制 MFA；经销商可按企业或系统策略启用。
SEC-003 | 会话 | HttpOnly、Secure、SameSite Cookie；会话超时；敏感操作重新认证。
SEC-004 | 限流 | 登录、注册、找回密码、表单、搜索 API 设置速率限制。
SEC-005 | 权限 | 服务端权限校验，前端隐藏按钮不能作为权限控制。
SEC-006 | CSRF/XSS | 所有写请求具备 CSRF 防护；富文本进行白名单清洗；默认输出转义。
SEC-007 | 文件上传 | 限制 MIME、扩展名、大小；文件扫描；私有文件不直接公开。
SEC-008 | 日志 | 安全日志包含登录、失败、权限修改、导出、退款等。
=== END TABLE ===

16.2 隐私
只收集业务所需数据。营销订阅与账户注册分开同意。
Cookie 分为必要、分析、营销等类别，非必要类别按适用地区取得同意后加载。
提供隐私政策、Cookie 设置、数据访问/删除申请入口。
用户导出和删除流程由后台形成工单记录。
经销商上传的企业资质仅内部授权人员可访问。
16.3 儿童相关原则
=== TABLE ===
儿童数据处理 / 品牌产品面向儿童，但网站账号和交易面向成年人。注册流程不提供儿童档案、儿童社区、儿童公开内容或直接向儿童收集姓名、生日、照片、位置等个人信息。如未来新增面向儿童的互动功能，需单独进行隐私与合规设计。
=== END TABLE ===
16.4 支付合规
采用支付服务商托管字段或令牌化方式，网站服务器尽量不接触完整卡号。
不得记录 CVV。
支付 Webhook 签名校验，退款权限严格控制。
如采用信用卡支付，应按实际集成方式完成适用的 PCI DSS 范围确认。

22. 推荐技术架构
22.1 架构目标
技术实现应服务于 SEO、动态运营、角色权限和 B2B/B2C 业务。推荐采用前后端分离但同一产品团队可维护的架构，前台支持服务端渲染，后台采用 API 驱动。
=== TABLE ===
层 | 建议 | 职责
Web 前端 | Next.js / React 或等价 SSR 框架 | 品牌官网、用户中心、经销商中心。
管理后台 | React/Vue 管理端 | 内部运营后台，可与前台共享设计组件。
后端 API | NestJS、Laravel、Django 等成熟框架 | 鉴权、商品、价格、订单、经销商、CMS 业务。
数据库 | PostgreSQL | 核心事务数据。
缓存/队列 | Redis + Queue | 会话、缓存、异步邮件、索引、Webhook。
搜索 | OpenSearch/Algolia | 产品与内容搜索。
对象存储 | S3 兼容存储 + CDN | 图片、文件、私有经销商资料。
部署 | 容器化 + CI/CD | Staging、Production、可回滚。
监控 | APM + Error Tracking + Central Logs | 性能、错误、业务异常。
=== END TABLE ===

22.2 关键实现建议
核心业务逻辑放在后端，不把价格权限、经销商授权、折扣规则只写在前端。
CMS 可以自研轻量模块或使用成熟 Headless CMS，但商品、价格、订单、经销商应由业务后端掌控。
产品页面使用 SSR/ISR 等方式兼顾 SEO 与发布效率。
后台批量导入、图片处理、邮件和搜索索引放入异步队列。
通过 Feature Flag 控制 B2C 交易、经销商功能、市场功能逐步启用，但最终功能代码按完整需求实现。

附录 E. 设计与开发实施重点
先确定品牌视觉基础、产品分类、经销商业务规则、价格规则和市场范围，再进入高保真设计。
UI 设计从首页、产品列表、产品详情、经销商中心、后台商品管理五个代表性页面建立设计系统，再扩展全部页面。
数据库先建立用户、经销商、商品、SKU、价格、订单、内容、权限模型，避免后期因 B2B 需求返工。
后台 CMS 与商品管理在开发早期可用，以便内容团队同步整理旧站资产。
每个迭代都同时完成桌面和移动端，不把移动适配推迟到最后。
上线前至少进行一次完整 UAT，覆盖游客、用户、经销商成员、经销商管理员、内容运营、订单人员、超级管理员。
